How this exam thinks about agents

The whole semester has leaned into coding agents as the way real engineers work, so an exam that asks students to write working code from scratch on paper would punish them for taking the course seriously. Instead, every question is built around a skill the agent can't do for them: reading code carefully, finding bugs by inspection, writing the spec they'd hand to the agent, judging which of two implementations is better, and making design calls under uncertainty.

Question 1 Trace-through

This Python script runs to completion. Predict the value printed at A, B, and C. (.scalar() on a query result returns the single value from the first column of the first row — here, the count.)

from sqlalchemy import create_engine, text

engine = create_engine("sqlite:///:memory:")

with engine.begin() as conn:
    conn.execute(text("""
        CREATE TABLE notes (id INTEGER PRIMARY KEY, body TEXT)
    """))
    conn.execute(text("INSERT INTO notes (body) VALUES (:b)"), {"b": "first"})
    conn.execute(text("INSERT INTO notes (body) VALUES (:b)"), {"b": "second"})

try:
    with engine.begin() as conn:
        conn.execute(
            text("INSERT INTO notes (body) VALUES (:b)"), {"b": "third"}
        )
        n = conn.execute(text("SELECT COUNT(*) FROM notes")).scalar()
        print("A:", n)                           # ___
        raise RuntimeError("oops")
except RuntimeError:
    pass

with engine.begin() as conn:
    n = conn.execute(text("SELECT COUNT(*) FROM notes")).scalar()
print("B:", n)                                   # ___

with engine.begin() as conn:
    conn.execute(text("UPDATE notes SET body = 'OOPS' WHERE id = 1"))
    conn.execute(text("INSERT INTO notes (body) VALUES (:b)"), {"b": "fourth"})

with engine.begin() as conn:
    rows = conn.execute(
        text("SELECT id, body FROM notes ORDER BY id")
    ).all()
print("C:", [(r.id, r.body) for r in rows])      # ___

For B, write one short sentence explaining why.

Question 3 Specification

You're adding notification preferences to an app. Each user has settings for which events generate notifications, and via which channels. The known event types right now are: new_message, new_follower, mentioned_in_comment, group_invite. You expect the product team to ship roughly 5–10 new event types over the next year. Channels are stable and won't change: email, push, in_app. For every (event, channel) pair, the user can independently choose whether they want it. The default for new users is "everything on," with the one exception that mentioned_in_comment over push is off.

Write the schema spec. Cover all three:

  1. The shape decision. You could put one column per (event, channel) directly on the users table — a "wide" approach — or keep preferences in a separate table. Pick one and in one sentence say why, naming one specific concern from the spec above that drives the call.
  2. The actual SQL — CREATE TABLE statement(s) with column types, NOT NULL flags, defaults, and any keys.
  3. One ambiguity in the product spec above that affects the data model and that you'd want to nail down before handing this off to your agent. State the ambiguity in one sentence, and the call you'd make in one sentence.

Question 5 Short design

You need to test this function:

import stripe
from sqlalchemy import text

class ChargeError(Exception): pass

def charge_user(user_id: int, amount_cents: int, db) -> str:
    """Charge the user's saved payment method via Stripe.
    Returns the Stripe charge id. Raises ChargeError on failure.
    Records an audit row in 'charges' on success."""
    row = db.execute(
        text("SELECT stripe_pm_id FROM payment_methods WHERE user_id = :u"),
        {"u": user_id},
    ).first()
    if row is None:
        raise ChargeError("no payment method on file")

    intent = stripe.PaymentIntent.create(
        amount=amount_cents,
        currency="usd",
        payment_method=row.stripe_pm_id,
        confirm=True,
    )
    if intent.status != "succeeded":
        raise ChargeError(f"stripe returned {intent.status}")

    db.execute(
        text("INSERT INTO charges (user_id, amount_cents, stripe_id) "
             "VALUES (:u, :a, :s)"),
        {"u": user_id, "a": amount_cents, "s": intent.id},
    )
    db.commit()
    return intent.id

Sketch the test plan. Cover all three:

  1. Boundaries. For each of (a) the database and (b) the Stripe API, say whether your tests use the real thing, an in-memory or test version, or a mock — and why, in one sentence each.
  2. Three tests, one per behavior: (i) the lookup of the payment method, (ii) the Stripe charge call, (iii) the audit-row insert. For each, give a def test_* name and 3–5 lines of pseudo-code showing the key assertion.
  3. One obvious-looking test you would NOT write, with one sentence on why — something a less-careful tester would think they need but would actually be noise or a trap.
